# Validation pipeline: generic severity-aware behavior, split error shape, and a dedicated validate endpoint

The FRS distinguishes Critical (blocking) from Warning (non-blocking) validation issues (§5.4/§8) and references a "validate endpoint" in prose (§5.4) that's missing from the API table (§10) — a real spec gap. Separately, the `422` shape in §10.5 is field-keyed and doesn't fit non-field business-rule failures like closure conditions or self-approval rejection. We resolved both together:

- **`POST /api/claims/validate`** — a new MediatR `Query` (no state change), filling the spec gap. Shares `CreateClaimCommandValidator` with the real create command, always returns `200` with every Critical + Warning issue found, never throws. This is the "tell me what's wrong" surface the Angular FNOL form uses per-step (§11.2); the create endpoint itself doesn't need to carry warnings inline in its success response because of this.
- **Severity uses FluentValidation's native `Severity` enum directly** (`Error` default = Critical, `Severity.Warning` = Warning) — no custom enum.
- **One generic `ValidationBehavior<TRequest, TResponse>`** pipeline behavior throws (→ `422`, `errors` dict) only on `Severity.Error` failures. Warning-severity failures are collected onto the command via a shared `IHasValidationWarnings` marker interface (a settable `Warnings` list) rather than audited by the behavior itself — for creation commands, no `ClaimId` exists yet at validation time to audit against.
- **Handlers, not the pipeline behavior, write `VALIDATION_ISSUE_ADDED`** audit entries for any warnings attached to their command, in the same transaction as their other audit writes (e.g. alongside `CLAIM_CREATED`), once a persisted id exists. Applies uniformly to every command with Warning-severity rules (currently: claim creation, reserve creation).
- **The `422` body gets a second array, `blockingConditions`**, for failures that aren't about one submitted field — closure conditions (`CC-01`–`CC-04`), invalid status transitions, self-approval rejection (`BR-R-03`). Entries are structured (`{ "code": "CC-01", "message": "..." }`, using the existing `BR-*`/`CC-*` rule IDs as codes), feeding §11.3's Closed-transition pre-flight checklist UI, which needs named, individually-checkable items, not opaque text.
- **Implementation split following from the above**: `errors` comes from FluentValidation via the pipeline behavior; `blockingConditions` comes from domain/business-rule checks inside handlers (these often need to inspect multiple related entities — e.g. a claim's current reserves — which isn't a natural field-validator concern) that throw a dedicated exception type, caught by the same exception-handling middleware as [ADR-0006](0006-exception-to-status-code-mapping.md) and mapped to the `blockingConditions` shape.

## Considered Options

- **Mutating `TResponse` generically to carry warnings inline on every command's success response.** Rejected: intrusive (every response DTO would need to implement a warnings-carrying interface), and redundant once a dedicated validate endpoint exists as the canonical "tell me what's wrong" surface.
- **Force-fitting closure-condition/transition failures into the field-keyed `errors` dict under a synthetic key** (e.g. `"_general"`). Rejected: loses the structured `{code, message}` shape the pre-flight checklist UI needs, and conflates "this field's value is wrong" with "this business rule about the whole aggregate is violated."

## Consequences

Two different exception types now feed one `422` response shape: FluentValidation's `ValidationException` → `errors`; a custom `BusinessRuleViolationException` → `blockingConditions`. In practice a single request only ever triggers one or the other, because `blockingConditions`-style checks live in handlers that only run after the FluentValidation pipeline has already passed clean — but the exception-handling middleware's merge behavior for the (currently theoretical) case of both firing should stay explicit rather than silently dropping one.
